# Architecture

**Analysis Date:** 2026-03-20

## Pattern Overview

**Overall:** Monorepo with layered, domain-driven frontend and headless CMS backend communicating via REST API.

**Key Characteristics:**
- Frontend-backend separation via REST API at `http://localhost:1337/api`
- Effect-TS for typed async/error handling throughout frontend service layer
- Server-driven rendering with client-heavy interactive components
- Clerk for authentication, synced to backend via webhook
- Database transactions for atomic money transfers across cards

## Layers

**Frontend Application Layer:**
- Purpose: Next.js 16 App Router with route groups, manages UI and user interactions
- Location: `bank-dash-app/src/app`
- Contains: Route group structure `(auth)` and `(home)`, page components, root layout with Clerk provider
- Depends on: Service layer via Effect, component library, utilities
- Used by: Browser clients; calls backend via service layer

**Frontend Service Layer:**
- Purpose: Abstracts all backend API communication; creates Effect-TS programs for async operations
- Location: `bank-dash-app/src/services`
- Contains: `*.ts` files (raw ApiClient fetch operations), `*.effect.ts` files (Effect-TS wrapped programs for component use)
- Depends on: ApiClient singleton, requestEffect wrapper, Zod schemas for validation
- Used by: Components (via server actions and Effect runtime) and backend webhook handler

**Frontend Component Layer:**
- Purpose: Renders UI using Radix UI primitives and custom components
- Location: `bank-dash-app/src/components`
- Contains: Feature components (DashboardSections, QuickTransfer, CardDetails), UI primitives (shadcn-style components in `ui/`), layout components (Sidebar, DashboardHeader)
- Depends on: React 19, hooks, services, types
- Used by: Page components and other components

**Frontend Cross-Cutting Infrastructure:**
- Purpose: Provides runtime, error handling, auth utilities, constants
- Location: `bank-dash-app/src/lib`, `bank-dash-app/src/constants`, `bank-dash-app/src/utils`, `bank-dash-app/src/hooks`
- Contains:
  - `lib/effect/runtime.ts`: Effect-TS runtime runner with optional DevTools
  - `lib/auth.ts`: Cached Clerk auth wrapper
  - `lib/errors/handleApiError.ts`: API error parser for field and status errors
  - `constants/error.ts`, `cache.ts`, `route.ts`: Centralized constants
  - `hooks/useUnsavedChanges.ts`: Reusable modal interaction hook
- Depends on: Effect library, Clerk SDK, Next.js APIs
- Used by: Services, components, pages

**Backend Content Layer (Strapi Auto-Generated):**
- Purpose: Standard CRUD collections generated by Strapi
- Location: `bank-dash-server/src/api/card`, `bank-dash-server/src/api/member`, `bank-dash-server/src/api/transaction`
- Contains: Schema definitions, auto-generated controllers, services, and routes
- Depends on: Strapi core factories
- Used by: Frontend service layer and transfer service

**Backend Custom Business Logic Layer:**
- Purpose: Complex business logic requiring atomicity (fund transfers with multi-card/multi-transaction operations)
- Location: `bank-dash-server/src/api/transfer`
- Contains:
  - `controllers/transfer.ts`: Request handler that delegates to service
  - `services/transfer.ts`: Atomic transfer implementation using Knex transactions
  - `routes/transfer.ts`: Custom POST /transfers endpoint
- Depends on: Strapi context, Knex query builder, database transactions
- Used by: Frontend transfer requests (no authentication required currently)

**Backend Infrastructure Layer:**
- Purpose: Database, configuration, plugin setup
- Location: `bank-dash-server/config`, `bank-dash-server/src/admin`, `bank-dash-server/src/extensions`, `bank-dash-server/src/middlewares`
- Contains: Database configuration (SQLite default), environment setup, Strapi plugin definitions
- Depends on: Strapi framework, better-sqlite3
- Used by: All other backend layers

## Data Flow

**Card Fetch Flow (Dashboard):**

1. Next.js page component calls `MyCardsSection` (Server Component)
2. Component awaits `runServerEffect(getCardsEffect(userId, 1, 2))`
3. `getCardsEffect` builds Effect program that:
   - Creates ApiClient GET request to `/cards?populate=*&filters[member][clerkId][$eq]={userId}&pagination[page]=1&pagination[pageSize]=2`
   - Wraps error handling via `requestEffect`
   - Adds cache tags and revalidation settings
   - Maps response to `{ cards, error }`
4. Runtime executes Effect program via `runServerEffect` → `Effect.runPromise`
5. `MyCardsSection` receives `cards: CardsResponse | null` and renders
6. Backend returns typed Strapi response with pagination metadata

**Transfer Flow (Quick Transfer):**

1. Client component submits form with sender/recipient/amount
2. Server action calls backend POST `/transfers` endpoint
3. Transfer controller receives request, validates fields
4. Transfers to `strapi.service('api::transfer.transfer').transfer()`
5. Transfer service:
   - Opens Knex database transaction
   - Queries sender's active published cards via member clerkId
   - Finds card with sufficient balance (using integer-cent arithmetic)
   - Queries recipient's active published cards
   - Creates withdrawal transaction (draft + published rows)
   - Creates deposit transaction (draft + published rows)
   - Links transactions to respective cards with ordering
   - Updates both card balances atomically
   - Commits transaction or rolls back on failure
6. Returns `{ success: true, error: null }` or error message
7. Frontend receives result and updates card list via cache invalidation

**Authentication & Member Sync:**

1. User signs up via Clerk UI at `/sign-up`
2. Clerk fires webhook to `POST /api/webhooks` (Next.js Route Handler)
3. Webhook handler:
   - Decodes and validates Clerk WebhookEvent
   - Extracts user data (id, email, name)
   - Calls backend POST `/members` to create member record
   - Links member to Clerk user via `clerkId` field
4. Frontend uses `getAuth()` to get Clerk session
5. All API calls filter by `clerkId` to isolate user data

**State Management:**

- No global state manager (Redux, Zustand) used
- Server Components use async/await for data fetching
- Client Components use React hooks (useState, useEffect) for local UI state
- Form state via react-hook-form with Zod validation
- Cache invalidation via Next.js `updateTag()` and cache tags

## Key Abstractions

**ApiClient Singleton:**
- Purpose: Centralizes all fetch operations with consistent error handling
- Examples: `src/services/api.ts`
- Pattern: Singleton class with static factory method, returns Effect programs for each HTTP method

**Effect-TS Error Handling:**
- Purpose: Typed, composable async operations with explicit error modeling
- Examples: `src/services/cards.effect.ts`, `src/services/api.effect.ts`
- Pattern:
  - Define error types as Schema.TaggedError (ApiError, NetworkError, ApiRequestError)
  - Wrap raw ApiClient calls with `requestEffect` to normalize errors
  - Use Effect.pipe, Effect.flatMap, Effect.catchAll for composition
  - Add Effect.withSpan for distributed tracing

**Zod Schemas with Type Inference:**
- Purpose: Runtime validation + TypeScript types from single source of truth
- Examples: `src/types/card.ts`, `src/types/member.ts`
- Pattern: Schema.Struct definitions that produce `z.infer` types

**Server Actions with Service Layer:**
- Purpose: Bridge between async frontend user actions and backend services
- Examples: `src/services/cards.ts` (addCard, updateCardDetails)
- Pattern:
  - Marked with `'use server'`
  - Accept user input, validate via schemas
  - Call Effect programs via `runServerEffect`
  - Return typed result object `{ error: string | null, data?: T }`
  - Handle cache invalidation with `updateTag()`

**Strapi Custom Endpoints:**
- Purpose: Encapsulate business logic requiring database transactions
- Examples: `bank-dash-server/src/api/transfer`
- Pattern:
  - Custom routes.ts defines POST path
  - Controller validates input and dispatches to service
  - Service uses Knex transaction for atomicity
  - Returns success/error response

## Entry Points

**Frontend Root:**
- Location: `bank-dash-app/src/app/layout.tsx`
- Triggers: Next.js server startup
- Responsibilities: Wraps app in ClerkProvider, loads global CSS, renders Toaster

**Frontend Auth Routes:**
- Location: `bank-dash-app/src/app/(auth)/layout.tsx`, `sign-in/page.tsx`, `sign-up/page.tsx`
- Triggers: User navigates to `/sign-in` or `/sign-up`
- Responsibilities: Delegates to Clerk-managed components, redirects authenticated users to `/dashboard`

**Frontend Home Routes:**
- Location: `bank-dash-app/src/app/(home)/layout.tsx`, `dashboard/page.tsx`, `cards/page.tsx`, etc.
- Triggers: Authenticated user navigates
- Responsibilities: Checks auth via `getAuth()`, renders Sidebar + main content, loads data via services

**Frontend Webhook:**
- Location: `bank-dash-app/src/app/api/webhooks/route.ts`
- Triggers: Clerk webhook on user signup (POST /api/webhooks)
- Responsibilities: Creates member record in backend, links to clerkId

**Backend Collections:**
- Location: `bank-dash-server/src/api/{card,member,transaction}/`
- Triggers: Strapi initialization
- Responsibilities: Expose REST endpoints for CRUD operations

**Backend Transfer Endpoint:**
- Location: `bank-dash-server/src/api/transfer/routes/transfer.ts`, `controllers/transfer.ts`, `services/transfer.ts`
- Triggers: Frontend POST /transfers
- Responsibilities: Executes atomic fund transfer with validation

## Error Handling

**Strategy:** Explicit error types modeled in Effect-TS; errors propagate as typed values, not exceptions

**Patterns:**

1. **Network Errors (ApiClient level):**
   - `NetworkError` when fetch itself fails (no response)
   - Caught in ApiClient.request → wrapped as NetworkError
   - Example: offline, DNS failure, timeout

2. **HTTP Errors (API response level):**
   - `ApiError` when response.ok is false or response.status is 204
   - Thrown from ApiClient, caught in requestEffect
   - Mapped to ApiRequestError with message and status

3. **Validation Errors (Business logic level):**
   - ApiRequestError details include field-level errors from Strapi ValidationError
   - Parsed in handleApiError → FieldErrors record
   - Consumed by forms to show field hints

4. **Component-Level Error Handling:**
   - Services return `{ error: string | null, data?: T }`
   - Components check error and render error UI (e.g., red box with message)
   - Example: MyCardsSection renders error div if cards fetch fails

5. **Webhook Error Handling:**
   - WebhookError with MESSAGES and status
   - Caught and logged with cause
   - Always returns HTTP response (may be error status)

## Cross-Cutting Concerns

**Logging:**
- Console errors logged in:
  - `src/services/api.effect.ts`: API error logs with message, status, cause
  - `src/app/api/webhooks/route.ts`: Webhook errors logged with full cause
  - Backend Strapi logs via `strapi.log.error()`
- No structured logging service; relies on browser console and server logs

**Validation:**
- Frontend: Zod schemas in src/types/ enforce runtime type safety
- Form validation: react-hook-form + Zod resolver
- API responses: requestEffect checks for error objects even when status 200
- Backend: Strapi built-in validation on schema fields

**Authentication:**
- Clerk manages session via @clerk/nextjs
- Frontend caches auth via `getAuth()` to deduplicate within request
- Backend: Clerk webhook creates member; clerkId used as user identifier
- Transfer endpoint currently has auth: false (no protection)

**Caching:**
- Next.js cache tags: `CACHE_TAGS.CARDS`, `CACHE_TAGS.CARD_DETAIL(id)`
- Revalidation times: `REVALIDATE.CARDS = 60`, `REVALIDATE.CARD_DETAIL = 3600`
- Cache invalidation: `updateTag()` after mutations (add/update card)
- Cache headers in service calls: `next: { revalidate, tags }`
